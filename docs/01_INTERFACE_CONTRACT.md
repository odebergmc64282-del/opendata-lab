## 1. 数据流程与模块边界

| 负责模块 | 已确认的交接约定 |
| --- | --- |
| A · 采集 | 按城市请求 Open-Meteo 的每日天气预报，向清洗模块提供原始 JSON。采集模块负责处理请求超时和异常响应。 |
| B · 清洗 | 整理为每个城市、每个预报日期一条标准记录，统一日期和单位，校验数值并去重。降水量缺失时保留为空。 |
| C · SQLite 与集成 | 初始化数据库和表，批量写入清洗结果，按城市和日期范围查询，并串联采集、清洗和入库。 |
| D · Streamlit | 使用城市和日期范围筛选，展示每日气温、降水及最近更新时间，并处理空查询结果。 |

正式契约定义了五个 Python 函数接口。当前资料只支持确认上述模块职责。五个函数的名称、所属模块、参数、默认值、返回值及类型均待原件核对。任务书与早期教学示例曾使用不同的数据形态（`dict`、`list[dict]`、`DataFrame`），各函数的实际输入输出以正式契约为准。

## 2. 标准数据

首版覆盖广州、北京和上海的每日天气预报。以下列出可确认的字段含义，字段名、精确类型、日期格式、度量单位和空值表示均待原件核对。

| 字段含义 | 已确认的规则 |
| --- | --- |
| 城市 | 与预报日期共同标识一条日预报记录。 |
| 预报日期 | 按日记录，清洗时统一日期表示。 |
| 每日最高温 | 清洗时统一单位并校验数值。 |
| 每日最低温 | 清洗时统一单位并校验数值。 |
| 每日降水量 | 清洗时统一单位并校验数值。缺失时保留为空，和测得的零降水区分。 |

最近更新时间是展示需求。其来源、是否属于标准记录、字段名和类型待原件核对。

## 3. SQLite 主键、写入与查询

- 表名为 `weather_daily`。
- 主键的业务组成是城市与预报日期。SQL 列名和声明类型待原件核对。
- 批量写入采用 UPSERT。同一城市、同一预报日期再次写入时更新已有记录，保留一条日预报记录。冲突时更新哪些列以及写入函数的返回约定待原件核对。
- 支持按城市和日期范围查询。日期边界是否包含、结果排序、返回类型及空结果表示待原件核对。

## 4. 异常和测试

| 场景 | 可确认的验证要求 |
| --- | --- |
| 请求超时、异常响应 | 用模拟响应验证采集模块能处理失败。异常类、重试策略和向调用方传播的方式待原件核对。 |
| 数值校验、缺失降水、重复记录 | 验证清洗结果保留缺失降水，并且每个城市、每个预报日期只保留一条记录。无效值和重复值冲突的处理策略待原件核对。 |
| SQLite 读写及重复刷新 | 用临时数据库验证建表、批量写入、条件查询，以及重复刷新会更新已有行而不会增加同键记录。 |
| 空查询与联调 | 验证空查询在界面上有明确提示，并跑通采集、清洗、入库、查询和展示。 |
